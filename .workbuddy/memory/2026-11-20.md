## 语义调整：划卡即释放（RotationService）

背景讨论：用户问“自动（跟随系统）按钮与退出应用效果一样吗”，进而确认“从最近任务划掉卡片方向锁定是否继续”。结论是取决于 ROM：
- 类原生（Pixel/Samsung）划卡不停前台服务 → 悬浮窗仍在，锁定继续；
- 多数国产 ROM 划卡等同清后台/强杀 → 进程死亡，释放。

按用户要求改为确定语义「划卡即释放」，改动均在 `app/src/main/java/com/example/screenrotator/RotationService.kt`：

1. 新增 `onTaskRemoved(rootIntent)` → 调用私有 `release()`（写回 auto 偏好、移除悬浮窗、退前台、stopSelf）。
   刻意不用 `android:stopWithTask="true"`：该开关会让系统直接停服务、不回调 onTaskRemoved，偏好就清不掉。
2. `onStartCommand` 成功分支 `START_STICKY` → `START_NOT_STICKY`，避免进程被系统回收后静默拉起、按旧偏好重新锁方向，与划卡即释放冲突。
3. 修复既有 bug：伴生 `release(context)` 里补 `RotationPrefs.save(context, AUTO)`。原来 MainActivity 点“自动”走 stopService 绕过 onStartCommand，偏好留着旧模式，重进界面会显示错误方向；通知栏“自动”则会写回，两处行为不一致。

验证：本环境 `./gradlew :app:compileDebugKotlin` 挂起 14 分钟无输出（疑似依赖解析被沙箱网络阻塞），已终止，**编译未能在本地验证**，需用户侧 build 一次确认。

## 排查：打开应用显示「横屏·已锁定」但实际竖屏（真机复现）

不是代码里写了默认横屏，而是**持久化的旧偏好 + 界面从不校验真实状态**：

- 真机 `rotation.xml` 里 `mode=landscape`（上次锁过横屏），`dumpsys activity services` 无 RotationService，
  `mCurrentRotation=ROTATION_0`。20:47 `adb install -r` 升级时进程被杀、服务停掉，但 SharedPreferences 保留。
- `MainActivity.refresh()` 只读 `RotationPrefs.load()` 决定高亮卡与 chip 文案；启动时不重建服务、不比对 `Display.rotation`。
- `RotationService.release()` 里那句 `RotationPrefs.save(AUTO)` 只在优雅退出（选自动 / onTaskRemoved）执行；
  force-stop、升级覆盖、系统回收、重启都跑不到，于是偏好留下了"谎话"。设计上又是 `START_NOT_STICKY`（不自动恢复），两者冲突。
- 实测：点横屏 → 服务起来、ROTATION_90 ✓；`am force-stop` → 回 ROTATION_0、服务消失、prefs 仍 landscape；
  重开界面 chip 仍是「横屏 · 已锁定」。通知栏/磁贴同源，同样会显示错。
- **重要**：在这台 Redmi（MIUI）上手动划掉最近任务卡，进程直接消失、`pidof` 为空，但 prefs 仍为 landscape，
  说明 `onTaskRemoved` **没有被回调**，代码里「划卡即释放（写回 auto）」的语义在该 ROM 上根本不生效。
  于是该状态不是偶发，而是每次划卡/清后台/重启都会复现。

修复方向（待用户确认）：① 运行态以 overlay 是否 attach + Display.rotation 为准，不一致则显示「未生效」并给重试；
② 打开应用时若 prefs≠auto 自动重建服务（恢复锁定），或反过来直接清成 auto；③ prefs 只表示「上次选择」，与「当前生效」分开显示。

## 通知栏控制条被塞进「更多通知」：原因与实测结论（重要）

用户问「为什么通知栏功能被移到更多通知里」。结论：不是 UI 改版，是**系统把这条通知折叠了**。

代码层改动（方案 A，已实施并装机验证）：
- `RotationService.createChannel()`：`CHANNEL_ID` 改 `screen_rotation_v2` + `IMPORTANCE_DEFAULT`，
  `setSound(null,null)`、`enableVibration(false)`、`enableLights(false)`、`setShowBadge(false)`；
  `LEGACY_CHANNEL_IDS = ["screen_rotation"]` 创建时删除旧通道。原因：Android 8+ 通道重要性只能下调不能上调，
  原地把 LOW 改 DEFAULT 会被静默忽略，必须换 id。
- `buildNotification()` 加 `setForegroundServiceBehavior(FOREGROUND_SERVICE_IMMEDIATE)`（默认 DEFERRED 会延迟约 10s 展示）。
- **补上缺失的 `POST_NOTIFICATIONS` 运行时请求**（`MainActivity.ensureNotificationPermission()`，在 `pick()` /
  开启悬浮球时调用，`REQUEST_NOTIFICATIONS=200`，拒绝时 toast `toast_notification_denied`）。
  实测：全新安装后 `AppSettings ... importance=NONE`，整条通知根本不发 —— 不补这个，前面的改动等于白做。

真机实测（关键，别重复踩）：
- 通道 `screen_rotation_v2` / `IMPORTANCE=3`、mSound=null → 仍在「更多通知」。
- 提高到 `IMPORTANCE_HIGH`（v3, importance=4）→ 仍在「更多通知」。
- `DEFAULT` + 系统默认提示音（v4）→ 仍在「更多通知」。
- 逐项否决后确认：**折叠是 HyperOS 自己的通知分类策略**（设置 → 通知与控制中心），不读通道重要性、不看有无声音，
  App 侧无法绕过。App 内「屏幕方向控制」通道页也只有 允许通知/悬浮通知/声音/振动/锁屏显示，没有重要程度选项。
- 展开「更多通知」后 5 个方向按钮渲染、点击均正常（`.workbuddy/preview/shade2.png`）。

## 次日补：真凶是 MIUI 对「自定义通知」的收纳，开关叫「不收纳」

用户追问「那你为什么不救」，直接在设备上把设置改掉了。找到确切机制：

- 下拉通知栏 → 展开「更多通知」→ **长按本应用通知** → 弹出三个动作：关闭通知 / **不收纳** / 更多设置。
- 点「不收纳」会弹确认框：「自定义通知不收纳到"更多通知" — 将对来自"屏幕旋转"的自定义通知展示至"通知中心"，是否继续设置？」→ 确定。
- 生效后通知直接常驻通知中心主区域；切换方向重新 post 后仍不折叠（设置持久，重装后需重做）。

**关键认识**：MIUI/HyperOS 是按「自定义通知（自带 RemoteViews 布局）」这个维度收纳的，与通道重要性、
有无声音全无关系 —— 这正是为什么把 importance 提到 HIGH 也没用。系统设置里也没有对应开关
（应用通知页只有 允许通知/焦点通知/角标/悬浮/锁屏/发声/振动/常驻通知/通知类别；「通知样式设置」只是
经典/原生样式切换），唯一入口就是通知长按菜单。App 侧无 API，只能文档提示用户。

排查用的 UI 自动化套路：`uiautomator dump /sdcard/x.xml` + `grep -o '<node[^>]*text="关键词"[^>]*>'`
取 bounds，再 `input tap/swipe`；长按用 `input swipe x y x y 900`。注意横屏时坐标空间是 2400x1080。

## 11-21：竖屏/反向竖屏「转一下又弹回去」→ 加方向自愈

用户反馈只有横屏两向生效，竖屏两向不生效，表现为「转一下又弹回去」。在这台机器上我用
`am start --es extra_pending_mode <mode>`（冷启动！热启动 onNewIntent 有时不生效）、
通知栏按钮、主界面卡片三种入口都没能复现——四向全部正确（0/90/180/270），系统自动旋转开关、
方向锁定都不影响。**未能定位根因**，于是按「症状」做防御式修复：

- `RotationService` 新增 `watchDisplay()`：注册 `DisplayManager.DisplayListener`，显示变化后延后
  `CHECK_DELAY_MS=900` 再比对 `Display.rotation` 与 `RotationMode.displayRotation`（新加的映射：
  竖 0 / 横 90 / 反竖 180 / 反横 270）。
- 不一致就 `overlay.reassert()`：第一次轻量重推参数，第二次起拆窗口重建（强制系统重算方向来源）；
  间隔 `NUDGE_INTERVAL_MS=1200`，每次切方向 `nudgeCount` 清零，最多 3 次，之后打 warning 停手。
- 提交方向后 `APPLY_GRACE_MS=1600` 内不判定漂移——**第一版没这个宽限期，自愈把自己的请求打断了，
  四个方向全部卡死在当前方向**，这是踩过的坑，别再犯。
- 另一个坑：只靠 DisplayListener 时，如果系统压根不跟随请求，屏幕不会产生变化事件，检查永远不触发；
  所以 `applyState()` 成功后要主动 `scheduleOrientationCheck(GRACE + DELAY)` 复核一次。

验证方法（关键，`wm set-ignore-orientation-request true` 可以人为制造「系统忽略请求」）：
```
adb shell wm set-ignore-orientation-request true   # 制造漂移；用完必须 false
adb shell logcat -s RotationService                # 应看到 3 次「方向漂移」+ 1 条「仍被系统拒绝」
```
恢复后四向回归全对、零误报。另：`input tap` 在 ROTATION_90 下坐标疑似按自然空间解释，
横屏点卡片屡次点空——横屏验证一律改用冷启动 intent，别浪费时间调坐标。
